## 1. Executive Summary & Business Context
### 1.1 Problem Statement
Текущая зависимость от стороннего биллинг-агрегатора обходится компании в **4.5% от общего оборота**. Кроме того, отсутствие прямого контроля над логикой повторных списаний (dunning) приводит к агрессивным, неоптимизированным ретраям, из-за чего бизнес теряет до **18% активной абонентской базы ежемесячно** (непреднамеренный отток / *involuntary churn*).

Разработка собственного сервиса рекуррентных платежей (**Recurring Billing Core**) с прямой интеграцией с эквайринговыми шлюзами (PSP) позволит:
- Сократить комиссионную нагрузку за счет отказа от агрегатора в пользу прямого банковского эквайринга;
- Внедрить гибкую сетку умных ретраев (dunning) и контролируемый Grace Period;
- Снизить involuntary churn с 18% до целевых **≤ 8%** уже в первом квартале после релиза MVP;
- Обеспечить промышленный запуск MVP в сжатый срок — **6 недель**.

### 1.2 Business Goals & KPIs
| Goal ID | Business Objective | Target Metric / KPI | Measurement Method |
| :--- | :--- | :--- | :--- |
| **BG-01** | Снижение издержек на биллинг и эквайринг | Экономия до 2–2.5% от оборота за счет исключения комиссии агрегатора (4.5% -> прямой PSP) | Финансовый отчет по эквайрингу ежемесячно |
| **BG-02** | Сокращение непреднамеренного оттока (*Involuntary Churn*) | Снижение оттока из-за неуспешных списаний с 18% до **≤ 8%** | Ежемесячный когортный анализ оттока подписок |
| **BG-03** | Своевременный релиз ядра в Production | Запуск ядра в Production ровно за **6 недель** | Контроль спринтов по скоупу MVP |
| **BG-04** | Соответствие стандарту безопасности PCI DSS | Полное исключение хранения открытых платежных данных (SAQ A / SAQ A-EP) | Ежегодный аудит ИБ / PCI DSS самооценка |

## 2. Scope of Work

### 2.1 In Scope (MVP / Phase 1 — Срок: 6 недель)
- [x] **Billing Core Engine:** Микросервис управления жизненным циклом подписок, инвойсов и платежей.
- [x] **Валюта и период подписки:** Строго российский рубль (`RUB`) и ежемесячный расчетный интервал (`MONTHLY`).
- [x] **Безопасная токенизация:** Интеграция с PSP-формой, сохранение только `psp_token`, маски `card_last4`, `card_brand` и срока действия карты.
- [x] **Инициация списаний:** Поддержка Merchant Initiated Transactions (MIT) по сохраненному токену.
- [x] **Умный Dunning и Grace Period:**
  - Льготный период (Grace Period) — **7 календарных дней** с сохранением доступа пользователя.
  - Сетка повторных списаний при мягком отказе (*Soft Decline*): **День +1, День +3, День +7** (3 попытки ретрая).
  - Мгновенная приостановка (*Hard Decline*) при компрометации карты (`stolen_card`, `expired_card`) без спама в PSP.
- [x] **Календарная арифметика дат:** Обработка коротких месяцев и високосных лет с сохранением якорного дня (31 янв -> 28/29 фев -> 31 мар).
- [x] **Отмена подписки:**
  - Пользовательская: отмена в конце оплаченного периода (`cancel_at_period_end = true`).
  - Операторская (Саппорт): немедленная отмена (`cancel_at_period_end = false`).
- [x] **Управление возвратами (Refunds):** Полный и частичный возврат с валидацией непревышения оплаченной суммы инвойса и защитой от двойных кликов.
- [x] **Интеграция с Merchant Backend:**
  - Исходящие вебхуки с гарантией доставки через паттерн **Transactional Outbox**.
  - Криптографическая подпись каждого вебхука заголовком `X-Webhook-Signature` (`HMAC-SHA256`).
  - Обязательный заголовок `Idempotency-Key` (UUID v4) на всех изменяющих POST-эндпоинтах.
  - Таймаут PSP 10 сек с предварительной сверкой статуса транзакции перед ретраем (защита от двойных списаний).

### 2.2 Out of Scope (Explicitly Excluded / Phase 2)
- [ ] Мультивалютность (KZT, USD) — проектируется в виде ENUM в схеме, но логика конвертации и эквайринга вынесена в Фазу 2.
- [ ] Годовые (`YEARLY`) и недельные (`WEEKLY`) тарифные планы со скидками.
- [ ] Логика промо-триалов на 7–30 дней с отложенным первым списанием.
- [ ] Прямое хранение полного номера карты (PAN) и CVV/CVC (категорически запрещено).
- [ ] Поллинг базы данных со стороны монолита (заменен на событийно-ориентированную модель Outbox).

## 4. Functional Requirements (FR)
| Req ID | Priority | Requirement Title | Detailed Description | Acceptance Criteria |
| :--- | :--- | :--- | :--- | :--- |
| **FR-01** | Must | Управление жизненным циклом подписки | Создание (`POST /subscriptions`), просмотр (`GET /subscriptions/{id}`) и отмена (`POST /subscriptions/{id}/cancel`). Поддержка статусов: `TRIALING`, `ACTIVE`, `PAST_DUE`, `SUSPENDED`, `CANCELED`. | Все переходы между статусами валидируются конечным автоматом (FSM) с эмиссией событий в Outbox. |
| **FR-02** | Must | Календарная привязка якорной даты | Расчет даты следующего списания (`next_billing_at`) с фиксацией исходного дня месяца (`anchor_day`). | Для подписки от 31 января даты: 28 февраля (29 в високосный) -> 31 марта -> 30 апреля -> 31 мая. |
| **FR-03** | Must | Умный Dunning и Grace Period | При Soft Decline подписка переходит в `PAST_DUE`. Назначаются ретраи на День +1, +3, +7. Grace Period = 7 дней с сохранением доступа. | Если списание успешно на ретрае — статус возвращается в `ACTIVE`. Если все 3 ретрая провалились — переход в `SUSPENDED`. |
| **FR-04** | Must | Обработка Hard Decline | При получении фатальных кодов отказа эквайера (`card_stolen`, `card_lost`, `account_closed`, `invalid_card`) ретраи немедленно блокируются. | Подписка мгновенно переходит в `SUSPENDED`, эмиттится событие `subscription.suspended`. |
| **FR-05** | Must | Безопасная токенизация (PCI DSS) | Система принимает от фронтенда только токен карты (`psp_token`) и маскированные атрибуты (`card_last4`, `card_brand`, `exp_month`, `exp_year`). | База данных и логи сервиса не содержат полей PAN и CVV. |
| **FR-06** | Must | Возвраты средств (Refunds) | Выполнение полного и частичного возврата по инвойсу (`POST /invoices/{id}/refund`) с проверкой доступного баланса. | Повторный запрос с той же суммой или запрос на сумму, превышающую остаток оплаты, отклоняется с HTTP 422. |
| **FR-07** | Must | Идемпотентность API | Все изменяющие запросы требуют заголовок `Idempotency-Key` (UUID v4). Повтор запроса возвращает кэшированный результат. | Повторный вызов с тем же ключом не выполняет повторного списания у PSP и возвращает идентичный ответ. |
| **FR-08** | Must | Гарантированные Webhooks (Outbox) | Отправка вебхуков в монолит через таблицу `WEBHOOK_OUTBOX` с подписью `HMAC-SHA256` и экспоненциальным backoff. | При сетевом сбое монолита события не теряются и повторяются по расписанию вплоть до `DEAD_LETTER`. |

## 6. Business Rules & Domain Invariants
| Rule ID | Rule Name | Formal Logic & Invariants | Exception Handling |
| :--- | :--- | :--- | :--- |
| **BR-01** | **Month-End Anchor Clamping** | `target_date = clamp_to_month_end(anchor_day, target_year, target_month)`. Если день подписки 31, а в месяце 28/29/30 дней — списывать в последний день месяца. Возвращаться к 31-му числу при первой возможности. | Детерминированный расчет в модуле календаря. |
| **BR-02** | **Dunning & Grace Policy** | `grace_period = 7 дней`. Сетка ретраев: `T + 1d`, `T + 3d`, `T + 7d`. Максимум 3 ретрая (всего 4 попытки). Клиент сохраняет доступ все 7 дней. | При наступлении `T + 7d` и неудаче — перевод подписки в `SUSPENDED`. |
| **BR-03** | **Hard vs Soft Decline** | `if error_type == 'HARD': cancel_retries(); status = 'SUSPENDED'`. Если отказ классифицирован банком как неустранимый — никаких повторных списаний. | Защита мерчанта от блокировок и штрафов платежных систем (НСПК/МИР). |
| **BR-04** | **Refund Amount Guardrail** | `sum(successful_refunds) + request.amount_minor <= invoice.amount_minor`. Возврат сверх фактически списанной суммы невозможен. | Отклонение HTTP 422 с кодом ошибки `REFUND_EXCEEDS_PAYMENT_BALANCE`. |
| **BR-05** | **PSP Timeout Reconciliation** | Таймаут вызова PSP — 10 000 мс. При HTTP 504 / Connection Timeout повторное списание вслепую **запрещено**. | Сервис переводит платеж в `PENDING` и запрашивает статус транзакции у PSP по исходному `Idempotency-Key`. |
| **BR-06** | **Integer Currency Representation** | Все суммы хранятся и передаются как целочисленные копейки (`amount_minor = 29990` для 299.90 RUB). | Исключение ошибок округления стандарта IEEE 754. |

## 8. Assumptions & Dependencies
- Банк-эквайер (PSP) предоставляет тестовую песочницу и поддерживает механизм токенизации и MIT-платежей к концу 1-й недели проекта.
- Серверное время всех узлов синхронизировано по протоколу NTP (погрешность < 50 мс).
- Merchant Backend гарантирует идемпотентную обработку входящих вебхуков по `aggregate_id` и `event_id`.
